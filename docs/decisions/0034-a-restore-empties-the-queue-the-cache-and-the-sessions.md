# A restore empties the queue, the cache and the sessions it loads

- **Context.** Production keeps its queue, its cache and its sessions in the database (`docker-compose.production.yml` sets `QUEUE_CONNECTION`, `CACHE_STORE` and `SESSION_DRIVER` to `database`), and `docker/backup.sh` dumps every table, so a restore brings back the `jobs`, `cache`, `cache_locks` and `sessions` rows of the dump's moment. A job in that `jobs` table was waiting when the dump ran and has, in the normal course, run since: a worker started on it sends its mail a second time. The cache holds that moment's rate-limit counts, the scheduler's heartbeat and any overlap lock a scheduled task held then, which keeps that task from running until the lock expires: a day, for the heartbeat, whose `withoutOverlapping()` keeps Laravel's 1440-minute default (`routes/console.php`). The restore procedure the owner asked for on 2026-11-17, before the launch walk-through, had to say what becomes of them.
- **Decision.** Proposed by the session on 2026-11-17 and accepted by the owner with the merge of the pull request that adds this file and runbook "Restoring production" (the owner approves that pull request): after the load, with the queue worker and the scheduler still stopped, the restore empties `jobs`, `cache`, `cache_locks` and `sessions`. `failed_jobs` stays, as the record of what had failed before the dump, and nothing in it is retried before the mailbox has been read; the one exception is a restore under a new key, which empties it too, since that key can read none of it (runbook "Under a new key").
- **Consequence.** Nothing the dump caught waiting is sent twice, and what it caught that had not gone out before the damage is never sent: those messages keep their `email_logs` rows at `queued`, which is how they are found, and the mailbox says which left (runbook "Email triage"). Every session ends, so everybody signs in again, except in a browser that ticked Remember me, whose cookie still matches the restored `users.remember_token`. The rate limits kept in the cache start from zero; the per-address status-link cap is counted in `email_logs` (runbook "Author status links") and still counts the dump's rows. `cass:health` reads its `scheduler` row red until the scheduler's first run after `up` writes a heartbeat, within five minutes. Reviewer reminders are outside it: the restored `reviewer_reminders` lacks the rows written since the dump, so the next hourly run sends those reminders once more.
- **To reverse.** Delete the `TRUNCATE` step, with the `&&` that leads to it, from the chain in runbook "The database half", take the four tables out of the runbook's Q7 d, drop the `queued` line from runbook "After a restore", and say in those three places that the worker runs again what the dump caught waiting; no test covers it.
