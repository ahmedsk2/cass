# The custom-domain verification token is stored in plaintext

- **Context.** Spec section 9 asks for every token, domain verification included, to be stored as a SHA-256 hash. Every other token in the application is one, because it is a bearer credential arriving from a client. The domain token is a challenge nonce published in public DNS by design: it authorises nothing, it never appears in a request, and the organiser has to be shown it again when their DNS panel has eaten the record.
- **Decision.** The owner's: `CLAUDE.md`, the rule book the owner adopted with the merge of #32 on 2026-10-16 (`6ae4e9b`), says "Tokens are stored hashed; the DNS verification nonce is the one documented exception." `organizations.custom_domain_token` is stored and shown in plaintext. First argued on 2026-09-12 in Plan 6, Task 1, decision 1 (`e1be4f1`), and recorded in the backlog the same day as a deviation from spec section 9.
- **Consequence.** A hash would make showing the token again impossible without minting a new token and invalidating the record the organiser already published (backlog, 2026-09-12).
- **To reverse.** Hash the token where `ClaimCustomDomain` mints it (`app/Actions/Organizations/ClaimCustomDomain.php:67`) and compare the hash where `VerifyCustomDomain` reads it for `carriesToken()` (`app/Actions/Organizations/VerifyCustomDomain.php:41`); `ReleaseCustomDomain` clears it (`app/Actions/Organizations/ReleaseCustomDomain.php:31`). Drop the exception from `CLAUDE.md`, and invert the cases `grep -rln custom_domain_token tests` finds in its five files.
