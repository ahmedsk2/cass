# The legacy import carries neither author addresses nor passwords

- **Context.** `submission_authors.email` is NOT NULL, and the legacy database stores no author address at all: one `contact_email` per abstract and a text blob for the byline. All ten legacy user rows hold real `$2y$10$` bcrypt hashes, and spec 5.10 says the import creates "users (without passwords; they receive a reset link on first login)".
- **Decision.** Proposed by the session on 2026-09-12 (Plan 6, `e1be4f1`, recorded in the backlog the same day) and accepted by the owner with the merge of #NN, which adds this file (the owner approves that pull request). The author whose name best matches the contact address gets it, and every other author gets `legacy-{id}-{n}@import.invalid`, RFC 2606's reserved domain. Legacy passwords are not carried, although they would have worked: `legacy-review.md:276` records that `users.reset_token` doubled as the manager-invitation token, so a password on that platform was never the only way in.
- **Consequence.** Nothing can ever be delivered to an imported author, and the imported conferences are archived, so nothing tries; every invented address is a line in the import's manual-review report. Each imported user needs a password reset (runbook "Importing the legacy conferences").
- **To reverse.** Written from the design document and Plan 6's plan, not from the import's code: Plan 6, Task 10, decision 1 (`docs/superpowers/plans/2026-09-13-plan-6-launch.md`) for the addresses, and its "Importing legacy passwords" note for the hashes. Give each author the contact address or relax the column to nullable, which that decision rejects, or carry the ten hashes instead of an unguessable random password, and invert the import tests' `@import.invalid` assertions that Task 10 writes.
