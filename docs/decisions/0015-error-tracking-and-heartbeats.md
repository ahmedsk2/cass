# Error tracking speaks the Sentry protocol; the DSN and ping URLs stay out of the repository

- **Context.** Nothing reported an exception, a dead scheduler or a skipped backup to anyone (`docs/reviews/2026-10-16-expert-brief.md`, question 4 and work order B5 to B7). The brief left the tracker to the owner: Flare, a self-hosted GlitchTip, or similar.
- **Decision.** The engineering default the owner accepted on 2026-11-04 (Plan 9 summary): `sentry/sentry-laravel`, because one SDK and one variable, `SENTRY_LARAVEL_DSN`, work with Sentry's hosted free plan, a self-hosted GlitchTip and Bugsink. The owner chose Sentry's hosted free plan for the DSN, in the data region picked at sign-up (the EU is the recommendation); Sentry keeps events outside Saudi Arabia, so before the DSN is set the owner checks that transfer against the PDPL's cross-border rules and ships a release whose privacy page says so (`privacy.hosting_body` in `lang/en/public.php`). The privacy floor is in code, not the environment: no request bodies, no personal data, no Livewire, cache, HTTP-client or command-line breadcrumbs, no trace headers on outgoing requests or queued jobs (`trace_propagation_targets` empty, the package's tracing off), bound values kept out of database error messages (MySQL's own duplicate-entry text can still quote one), and `App\Support\Monitoring\ScrubTrackerEvent` dropping frame arguments, headers, query strings, link tokens and the metadata of log and Artisan-command breadcrumbs, and masking addresses. Heartbeats are pings on success: `cass:health --json --ping` hourly to `CASS_HEARTBEAT_URL`, and `curl` after each backup cron. The DSN and the three ping URLs are secrets, held by the application's environment and two root-only files on the host; this repository and `docs/HANDOVER.md` name the checks only.
- **Consequence.** An event shows the line, the route and the stack, never the abstract or the author; a data-dependent error is reproduced from the database. Choosing Flare later means `spatie/laravel-flare` and `FLARE_KEY` under the same privacy rules. By the owner's choice (Plan 9 summary, question 3), a Turnstile fail-open reaches the tracker only as a breadcrumb.
- **Amended 2026-11-05, at the deploy.** The owner keeps monitoring on services they already run, not on new accounts. The three heartbeats are Uptime Kuma push monitors (Kuma is a Coolify service on the host, `https://uptime.towardpcc.com`); the uptime probe is an OCI Health Checks monitor on `/up` with a Monitoring alarm to the tenancy's `hosting-alerts` topic, next to a Kuma HTTP monitor. UptimeRobot and Healthchecks.io are not used. The code did not change: Kuma's push route takes the same GET on success. Kuma shares the host, so the signal that survives the host going down is OCI's. Error tracking stays as decided; a self-hosted GlitchTip under Coolify, which speaks the Sentry protocol and would keep events in Riyadh, is the open alternative (backlog, "Monitoring").
- **Amended 2026-11-06, the tracker.** The owner chose GlitchTip, under Coolify on their own host, over Sentry's hosted plan, which closes the alternative above. Events stay in Riyadh, so nothing is transferred across the border and the PDPL transfer check falls away; the privacy page now says error reports are kept on the operator's own server in Saudi Arabia and are not sent to a third-party service (`privacy.hosting_body`). The SDK, `SENTRY_LARAVEL_DSN`, the privacy floor and the tracker test are unchanged, because GlitchTip speaks the Sentry protocol; the new-issue alert is configured in GlitchTip, an email to the owner. The cost is one more service on the host to run and back up. A hosted tracker later is a DSN change plus the transfer check and a privacy-page release that names the transfer.
- **To reverse.** Remove `Integration::handles()` from `bootstrap/app.php`, then `sentry/sentry-laravel`, `config/sentry.php` and `ScrubTrackerEvent`, and delete `tests/Feature/Security/ErrorTrackingTest.php` and `ErrorTrackingBootTest.php`; drop `--ping` from the hourly entry in `routes/console.php` and its cases in `tests/Unit/HealthCommandTest.php`.
